# Developer Tool Storage audit

7 November 2026 · macOS · read-only inventory of the requested locations

No cleanup commands were run. The audit used directory and file metadata, bounded source searches, process names and path evidence, tool inventory commands, and vendor documentation. It did not read conversation bodies, database rows, or simulator app data. DevCleaner’s in-progress worktree changes were used as implementation context. The classifications below are proposed product behavior.

## 1. Claude Desktop Cowork VM

- **Detection and use.** Anthropic documents that local Cowork executes code in an isolated VM. The on-disk bundle contains a 10.00 GiB `rootfs.img`, kernel and initrd, origin markers, EFI and identity files, and a writable-looking `sessiondata.img` (about 14 MiB allocated). This supports identifying the bundle as the Cowork execution environment. The scan found one populated bundle and two empty hash-named directories under `warm`. Inspection of the installed Claude Desktop 3.6556.2 application bundle found version/hash-based warm staging, foreground provisioning, and cleanup logic for older warm entries. The empty directories provide no evidence of another complete image. A current base and a staged update can coexist by design. Failed cleanup or interrupted downloads could leave stale staging entries. The October 22 base-image timestamp establishes a write date only. [Anthropic Cowork VM documentation](https://support.claude.com/en/articles/17828685-run-your-endpoint-detection-and-response-edr-sensor-in-claude-cowork-on-claude-desktop)
- **Safety and lifecycle.** An obsolete, failed, or interrupted download is plausible. Staleness needs a version or digest from an authoritative Claude manifest plus evidence that the app no longer references the generation. There was no visible Claude VM process or open `rootfs.img` handle in the sampled session. For future reporting, combine Claude Desktop and helper PID identity, Virtualization framework helpers, open backing-file and bundle-path checks, and any vendor VM/task status. Treat unreadable process data as unknown. After the app quits, it may still have an active helper or a pending warm download.
- **Mechanism, loss, and recovery.** Keep the VM read-only in DevCleaner. Use a vendor reset or storage action if Anthropic exposes one for the installed build. DevCleaner currently offers a REVIEW Trash action for the bundle contents. Replace that action with informational reporting because the same directory includes the session disk. The installed build supports automatic VM provisioning, conditional background prefetch, and a bounded auto-reinstall path after certain startup failures. That supports replaceability of the base payload. Recovery depends on the vendor service, feature configuration, free space, and the specific failure. This audit did not exercise redownload after removal or validate the lifecycle of every staging generation. The session disk and VM identity may contain state that cannot be recreated. Show 10.10 GiB occupied and zero actionable reclaim.
- **Tests before expanding.** Compare Cowork idle, active, and downloading on a disposable profile. Observe both cold provisioning and an app update, and identify which paths are regenerated. Test unreadable process state and a live VM helper holding the backing disk after the GUI closes.

## 2. Android Emulator AVD storage

- **Detection.** `emulator -list-avds` returned `medium_phone`. Its configured display name is Medium Phone. Total 9.89 GiB, with 7.28 GiB allocated to `userdata-qemu.img.qcow2` and 2.49 GiB under `snapshots/default_boot`. The bundled `qemu-img info --output=json --backing-chain` found an internal `default_boot` snapshot and a local `userdata-qemu.img` backing file. No matching emulator/QEMU process or visible open AVD path was observed. Lock files remained. Determine per-device state from the emulator PID and command arguments, live lock ownership, process file paths and, when already available, adb emulator serial-to-AVD-name mapping. Use a stopped/running/unknown status. Avoid starting adb or an emulator during background scans.
- **Last use and disposability.** There is no verified last-used field in this AVD. The latest userdata image write was October 25 and the embedded Quick Boot snapshot was dated October 22, Madrid time. Label these as activity proxies. Show default Quick Boot separately from named snapshots, and let the user tag QA devices or explicitly mark an AVD disposable. Age, name, and a small app count cannot establish disposability. Apps, account state, fixtures, evidence, and named restore points may be valuable.
- **Mechanism, loss, and recovery.** For a stale or invalid snapshot use the emulator’s Snapshots UI, which can also prompt for or automatically remove invalid snapshots after compatibility changes. A version-supported emulator console snapshot delete command can target an explicit snapshot on the correct running AVD, but DevCleaner should never boot a device just to remove a snapshot. Loss includes that saved restore point. Quick Boot can be recreated by a subsequent successful boot and save. Device Manager **Wipe Data**, or explicitly starting a stopped AVD with `emulator -avd <name> -wipe-data`, resets user data from the system image and removes installed apps and settings. Inspect separately configured SD cards, which the emulator’s documented wipe flag preserves. Full delete uses Device Manager or `avdmanager delete avd -n <name>`. It also removes the AVD definition. Device and apps can be rebuilt if inputs exist. Local state requires backup or recreation. All three actions require REVIEW. [Android snapshots](https://developer.android.com/studio/run/emulator-snapshots) · [Emulator command line](https://developer.android.com/studio/run/emulator-commandline) · [Emulator console](https://developer.android.com/studio/run/emulator-console)
- **Compaction and reclaim.** A generic offline QEMU conversion can produce a sparse copy of the current disk view, but may omit internal snapshots, change backing dependencies, or break emulator snapshot and encryption expectations. Keep compaction outside the product unless Android publishes a supported workflow. The 2.49 GiB snapshot folder is a footprint, since Quick Boot also references clusters in the qcow2 chain. Snapshot deletion may leave reusable clusters without shrinking the host file. Show unknown snapshot reclaim, whole AVD allocation as a delete estimate, and wipe as current affected allocation minus a comparable freshly initialized baseline when available. [QEMU image utility](https://www.qemu.org/docs/master/tools/qemu-img.html)
- **Tests.** Use disposable Play Store and Google APIs AVDs with default and named snapshots, an attached SD card, a moved data directory, a live and a stale PID lock, and a simulated process start between preview and execution. Verify apps and settings survive snapshot-only removal, and measure before/after blocks for each action. If researching compaction, test only copies and verify boot, snapshot restore, and app-data integrity.

## 3. Android SDK system images

- **Detection.** Local SDK manifests report `system-images;android-36;google_apis;arm64-v8a` (4.26 GiB) and `system-images;android-36;google_apis_playstore;arm64-v8a` (2.25 GiB). The one AVD visible in the current environment references the Play Store package in `image.sysdir.1`. No visible emulator or SDK image open-path use was found. The Google APIs image is unreferenced within this inventory. Custom AVDs and ad hoc consumers outside this inventory remain possible. With the installed Homebrew JDK supplied to the SDK tools, `avdmanager list avd` agreed with the emulator inventory, and `sdkmanager --list --channel=0` advertised both exact system image IDs at the installed revision (7) and both NDK IDs. This confirms catalog availability at scan time. Reinstallation was not exercised.
- **Safety conditions.** Enumerate installed packages by exact manifest ID and canonical SDK root, using Android Studio’s configured SDK, `ANDROID_HOME`, legacy `ANDROID_SDK_ROOT`, and explicit additional roots. Discover AVDs using the emulator’s effective root, environment overrides, and registered custom locations. Follow descriptor `path` and `path.rel` using tool semantics, and resolve every `image.sysdir.N` against the appropriate SDK or absolute path. Index canonical package paths rather than comparing API level alone. Include stopped AVDs and check active emulator/QEMU command arguments, `-sysdir` or image overrides, relevant open paths, and SDK/package manager activity. Require complete configured scope, no references or users, and an exact restorable package from the vendor catalog. Unknown roots, malformed descriptors, an unavailable catalog, or limited process visibility keep the candidate in REVIEW. Revalidate immediately before execution.
- **Mechanism, loss, and recovery.** Use Android Studio SDK Manager or `android sdk remove --sdk=<root> <package-id>`, confirmed in the installed Android CLI 1.0.16406183 help. The installed command-line tools also provide `sdkmanager --sdk_root=<root> --uninstall '<package-id>'`. Android now documents `sdkmanager` as deprecated. Reinstall the exact package ID through the same SDK manager. Recovery needs network, catalog availability, any required license, and disk space. Ad hoc scripts or future AVDs that depend on the image may fail until reinstalled. Report package allocation separately from eligible reclaim. [Android SDK package management](https://developer.android.com/tools/sdkmanager)
- **Tests.** Cover multiple SDKs, duplicate package IDs across roots, relative and absolute references, moved AVDs, missing configs, symlinks, custom runtime image arguments, unavailable packages, an active installation, and a use race. Run uninstall/reinstall with a disposable SDK and confirm a referenced neighboring image remains usable.

## 4. Android NDK versions

- **Detection and safety.** `27.1.12297006` and `27.0.12077973` each occupy 2.41 GiB. A bounded search of common Gradle configuration files in the development root surfaced no matching declaration. AGP selects a version compatible with that plugin when `ndkVersion` is omitted. An explicit `ndkVersion`, `ndkPath`, legacy `ndk.dir`, or a standalone CMake/NDK invocation can select a different installation. Trace version catalogs, root and module properties, convention plugins, included builds, React Native wiring, CI, and worktrees. Capture exact paths from recent local native build diagnostics or CMake cache metadata when available. Read metadata on demand and keep dynamically computed or unobserved requirements unknown. Never execute arbitrary Gradle configuration as a background probe. A package can be a candidate for manual review only after mapping configured native builds and pinned toolchains, including their AGP defaults, and checking active toolchain use. [Android NDK configuration](https://developer.android.com/studio/projects/install-ndk)
- **Mechanism, loss, and recovery.** Keep DevCleaner deletion blocked. Provide a handoff to SDK Manager for manual removal of `ndk;<version>` via the same package mechanism as images. Projects can fail to configure or build offline. Reinstalling the exact version depends on the catalog, licenses, network, and disk. Some AGP/Studio flows can download required versions, while a standalone toolchain path or offline build cannot rely on that. Show allocated bytes per version and zero DevCleaner reclaim.
- **Tests.** Build fixtures with explicit versions, different AGP defaults, dynamic conventions, side-by-side roots, legacy and custom paths, and standalone CMake. Check known/referenced/unknown status under failed configuration, active compilation, and missing repository visibility. Validate remove/reinstall in a separate SDK only.

| iOS 27.0 device | Allocated | State | Last used, Madrid time |

- **Detection.** Xcode 27.2’s `xcrun simctl list devices -j` returned 25 devices and provided `lastUsedAt` for all three large devices. Keep timestamps nullable and accept ISO 8601 with or without fractional seconds. Display runtime, availability reason, state, UDID, and size. Compare the service-reported size with allocated bytes under the reported device root if the user requests an accurate estimate. The two unavailable watchOS devices were in Creating state with a missing runtime profile. One had a 4 KiB device directory and the other no corresponding directory. Missing sizes elsewhere should display as unknown. `simctl listapps <UDID>` rejected a shutdown device, so query it on demand for booted devices. For shutdown devices, a bounded scan of installed app bundle metadata can supply a partial list without booting or opening app containers.
- **Safety and mechanism.** Existing DevCleaner already has device inventory and per-UDID deletion. It also labels unavailable devices SAFE and exposes `simctl delete unavailable`. Change unavailable deletion to explicit REVIEW with a preview of individual UDIDs. A different Xcode/runtime can change availability, and unavailable devices can retain valuable data. Revalidate Xcode selection, exact UDID, state, and favorite or QA tags. Protect running or transitional states. Treat both named QA devices as REVIEW and exclude them from default selections. A user-selected disposable device can use `xcrun simctl erase <UDID>`. Removal uses `xcrun simctl delete <UDID>`. Keep runtimes separate. The installed `simctl help` lists erase, delete, and listapps, with no generic stale-cache cleanup operation. Use only a separately documented owner-specific cache action if one is identified.
- **Loss, recovery, and sizing.** Erase removes apps, settings, and sandbox state while keeping the device definition. Delete also removes the definition. Recreating the device and reinstalling apps requires a compatible runtime and builds. App data, screenshots stored inside the device, credentials, and QA evidence may be unrecoverable. Measure delete footprint by device and report erase estimate as affected allocated data minus a comparable clean baseline. Include separately measured log storage only when the action demonstrably removes it. Exclude shared runtime allocations.
- **Tests.** Replay the current JSON, including missing size fields and Creating state. Test favorite and QA devices, unavailable devices with user data, Xcode selection changes, shutdown-to-boot races, and tool failures. On disposable devices, compare erase versus delete with a known app and data fixture. Verify unrelated devices and external QA evidence survive.

## 6. MeetScribe development and model caches

| Cache under `~/Library/Caches` | Total | Framework subtree |
| --- | ---: | ---: |

| `MeetScribeValidation` | 0.81 GiB | 0.80 GiB |
| `com.meetscribe.mac` | 0.21 GiB | 0.20 GiB |

- **Detection and provenance.** MeetScribe’s package defines the benchmark and validation executables. Its sources load local speech models through Core ML and its dependencies. The shared `com.apple.e5rt.e5bundlecache` layout contains OS-build-keyed bundles with BNNS, ANE, and MPS Graph artifacts. That strongly matches Core ML’s documented device specialization cache. The literal path is a framework implementation detail. Model inputs live separately, for example under MeetScribe’s storage root at `~/Library/Application Support/MeetScribe/Models`. The surrounding cache roots also contain `fsCachedData` and other entries whose contents were outside this verification. [Apple Core ML specialization and caching](https://developer.apple.com/videos/play/wwdc2023/10049/)
- **Safety, mechanism, and recovery.** Start with an app-specific inventory of these three owner paths. Core ML normally manages purging and re-specializes on a cache miss. With the input model already present, the expected cost is slower first model load and local regeneration, without fetching model weights again. The exact three paths were not cold-tested. Keep them REVIEW pending validation and prefer an owner-supported reset if one becomes available. Only a validated framework subtree could qualify for an app-specific SAFE rule. Preserve sibling cache data, Application Support, meetings, transcripts, and model inputs. Avoid an all-app rule keyed on the private directory name.
- **Sizing and tests.** Report about 2.93 GiB allocated across the three framework subtrees. To qualify a candidate, use a disposable account and synthetic speech with installed models and network disabled. Compare cold and warm benchmark, validation, and production inference. Confirm that the intended subtree is regenerated, model and meeting files are preserved, output is comparable, and startup latency is acceptable. Cover concurrent inference, inaccessible or redirected paths, and multiple OS builds.

## 7. npm and npx

- **Detection.** The installed npm is 10.9.9 and resolves its cache to `~/.npm` for the audited invocation. `_cacache` is the 0.28 GiB content-addressed download cache. `_npx` is 0.96 GiB across three cached execution environments. Two entries totaling about 0.48 GiB were visibly in use by Firebase MCP and Desktop Commander processes, via open executable files or a process working directory. The remaining entry occupies about 0.47 GiB and was unconfirmed. An older timestamp does not establish inactivity. Resolve the configured cache with the actual npm binary and environment. Validate the canonical root and subtree layout. Keep project `node_modules`, global npm prefix packages, and npm credentials outside the rule.
- **Mechanism and safety.** DevCleaner already offers SAFE filesystem cleanup for both paths. Prioritize making it command-backed and enforcing a live dependency gate. For downloads, use `npm cache verify` for integrity and garbage collection, or offer explicit `npm cache clean --force` for the full cache. Verification can modify the cache and belongs in an action. On an npm that supports it, enumerate `npm cache npx ls` and remove selected verified keys via `npm cache npx rm <key>`. The installed v10 help and docs lack that subcommand. On those installations, leave npx inventory-only. Before acting, inspect npm, npx and descendant processes, working directories, command paths, and open cache paths. Block unknown or active use and recheck at execution. [npm 10 cache commands](https://docs.npmjs.com/cli/v10/commands/npm-cache/) · [npm 11 cache commands](https://docs.npmjs.com/cli/v11/commands/npm-cache/)
- **Loss, recovery, and sizing.** An inactive cache is replaceable when the registry and credentials can serve the original dependencies. Offline builds can fail and an unpinned npx invocation can resolve a newer version. Treat offline dependency retention and unavailable packages as REVIEW. Use allocated bytes of eligible entries as the removal estimate. The full download-cache footprint is an upper bound for `verify`, whose exact reclaim is only known after it runs.
- **Tests.** Exercise both installed-command capabilities with isolated caches and a local package fixture. Include alternate cache roots, workspace `node_modules`, registry failure, an npx descendant with an open file but unrelated process name, and an active process appearing after preview. Verify that only selected npx keys are removed and reinstall works.

BuildGetcoparentia occupies 1.07 GiB, including about 0.87 GiB of session JSONL and 0.20 GiB of tool results. ## Product direction and implementation order

Use **Developer Tool Storage** as a top-level view over the existing providers. Group AI Worktrees, AI Agent Caches, Xcode Build Data, iOS Simulator Storage, Android Emulator Storage, Android SDK Images, Android NDK Versions, npm/npx Cache, SwiftPM / CocoaPods / Gradle, and App-specific Development Caches. Reuse process monitoring, the size scanner, cleanup planning, preview, and execution-time validation. Keep the labels **SAFE**, **REVIEW**, and **PROTECTED** consistent across summary and detail views. Show occupied bytes, potentially reclaimable bytes for a chosen action, and missing or incomplete evidence separately. Deduplicate overlapping roots and hard links. APFS clones, snapshots, sparse files, and Trash can all make the actual free-space change differ from allocated bytes. Keep process collection shared, cap directory walks, skip symlinks, and defer slow catalog, app, and project lookups to detail views or action validation.

1. **Harden existing actions first.** Move unavailable simulator deletion behind per-device REVIEW and replace whole-bundle Claude VM Trash with informational reporting. Add npm command capability and active-dependency checks. Surface existing Git-aware artifact cleanup here once its worktree safety tests pass.
2. **Ship read-only Android package and device details.** The 4.26 GiB Google APIs image is the strongest package-removal candidate. Add SDK Manager handoff under REVIEW first. Promote only when configured AVD scope is complete, direct use checks pass, and the exact package is restorable. Keep AVD snapshot deletion, wipes, and simulator erase explicit REVIEW. Show NDK evidence while preserving both versions.
3. **Validate a narrow MeetScribe rule.** Start with the benchmark and validation framework caches. Promote only after a disposable offline cold-load test. Leave Codex plugin and staging directories informational until owner-specific lifecycle evidence supports a narrower action. Keep Claude and Codex history protected.
4. **Surface existing Xcode and package-manager storage rules.** Xcode DerivedData can expose verified build and index outputs. Match the configured path and project metadata, require idle builders, and preserve archives, `.xcresult` evidence and signing material. Prefer Xcode’s Clean Build Folder for build products. Verified regenerable indexes can be considered separately, with a reindex/rebuild cost. SwiftPM has `swift package purge-cache` for its global repository cache, CocoaPods has `pod cache clean <pod>`, and Gradle has built-in retention for its managed caches. Scope these to verified cache roots, require idle tools and available dependency sources, and preserve user configuration, custom repositories, credentials and toolchains. Measure allocated affected entries, and test custom cache paths, cold rebuild and resolution, offline behavior, and preservation of QA artifacts. The default locations sampled for these categories were empty or small, so existing coverage is sufficient for this Mac. [CocoaPods command reference](https://guides.cocoapods.org/terminal/commands.html#pod_cache_clean) · [Gradle cache layout and retention](https://docs.gradle.org/current/userguide/directory_layout.html)
